# Phase 12.3 Plan 02: Extend ProposedNetwork PK with Revision Discriminator — Summary

One-liner: Replaced the empty `primary key ()` on `ProposedNetwork` with a composite `(Name, Revision)` PK and have `NetworkEngine.proposeRevision` auto-assign the next `Revision` via a SQL subquery, unlocking multi-revision proposeRevision tests for Plan 12.3-06.

## Goal

Fix the Group C schema design bug: `ProposedNetwork` had `primary key ()` (zero-column / singleton) that rejected a second `proposeRevision()` call with a UNIQUE-constraint failure. The schema intent (per network.spec.ts annotations) is "many proposed revisions per network". Make the change additive — no behavior change for existing single-revision tests — and leave unskipping to Plan 12.3-06.

## What Built

1. **Schema (`packages/vote-core/schema/votetorrent.qsql`):** Added `Revision integer not null` column to `ProposedNetwork` and changed `primary key ()` to `primary key (Name, Revision)`. All other CHECK constraints, FK semantics, and the `with context (...)` clause are unchanged.

2. **Engine (`packages/vote-engine/src/network/network-engine.ts:604-620`):** Updated the `proposeRevision` INSERT to include `Revision` in the column list with the value computed by `coalesce((select max(Revision) from ProposedNetwork where Name = :name), -1) + 1`. The engine signature, the `NetworkRevision` type, and the `INetworkEngine.proposeRevision` contract are unchanged — the discriminator is invisible to callers.

3. **Tests (`packages/vote-engine/test/network.spec.ts`):** Updated three raw-INSERT constraint tests (892, 2057, 2073) to bind the new `Revision` column. These tests verify `UserValid` CHECK behavior; their assertions are unchanged.

## Decisions Made

- **Add a new column rather than reuse one.** None of the columns currently inserted by the engine (`Name`, `ImageRef`, `Relays`, `TimestampAuthorities`, `NumberRequiredTSAs`, `ElectionType`) is unique across multiple proposeRevision calls — `Name` repeats by definition (same network), and the others can legitimately repeat. The plan's "preferred" option (reuse existing column) had no candidate.
- **Auto-assign Revision SQL-side instead of plumbing through the engine API.** The `NetworkRevision` interface has no `revision` field, and adding one would propagate into builders, mocks, fixtures, and every caller. A subquery in the INSERT statement is fully internal to `network-engine.ts` and preserves the contract.
- **Discriminator name = `Revision`** to match the canonical convention used by `ElectionRevision.Revision` and `ProposedElectionRevision.Revision`.
- **Use `coalesce(max(...), -1) + 1` rather than `coalesce(max(...)+1, 0)`** because quereus's coalesce of NULL + arithmetic might not short-circuit cleanly across all dialects; the chosen form starts the first revision at 0 unambiguously.
- **The select at `network-engine.ts:200-209` (getDetails) is unchanged for this plan.** It currently does `select ... from ProposedNetwork where Name = :name` with `.get()` (single row). With multiple rows present, behavior is undefined-but-deterministic; Plan 12.3-06 owns adding `ORDER BY Revision DESC LIMIT 1` if the unskipped tests require "latest revision" semantics.
