## Decisions Made

- **Why re-skip instead of unskip-and-pass?** The phase 12.3 success criteria explicitly allow re-skipping with a refined annotation when a different blocker surfaces. After fixing the Digest-input alignment, all 7 tests advanced past `Authority.InsertValid` (which previously failed) and now fail on `Admin.MutationValid` — a strictly deeper schema constraint. The 12.3-01 plan correctly fixed the Authority Digest contract; what it could not anticipate (and what no test-side plan can fix without engine surgery) is that `Admin.MutationValid` independently requires the same `InviteResult.Digest` to additionally encode the Admin and Officer payloads.
- **Why extend seedAuthorityInvite (Rule 2) instead of inlining?** Every one of these 7 tests needs the same alignment. Inlining would duplicate the same logic 7 times and would not benefit any other test. The override is optional with safe defaults, so no existing call site is disturbed (verified by full network.spec.ts run after Task 1).
- **Why not fix `respondToInvite` to accept admin/officer payload here?** That is a Rule-4 architectural change — it expands the engine's public surface (`respondToInvite` takes more typed input), changes the SQL `Digest()` call inside respondToInvite, and requires a coordinated update to `Admin.MutationValid` if the schema changes are warranted. None of those are in scope for a test-side plan whose stated work is "unskip / re-skip". The follow-up engine plan should own that change.
- **Why use `domainName: null` for the 'NoDomain' case at line ~549?** The test calls `createAuthority({ name: 'NoDomain' } as never, ...)` (no `domainName`). The engine binds undefined as null in the Authority insert, so `new.DomainName = null`. To make the InviteResult.Digest match, respondToInvite must also commit `null` for DomainName, which means the test must pass `domainName: null` to seedAuthorityInvite. This was the one non-obvious override.
