# Phase 12.3 Plan 03: Add seedUserInvite + seedBallot Test Helpers — Summary

One-liner: Added two composable Layer-2.5/Layer-3 fixture helpers in `test-context.ts` — `seedUserInvite` (officer-scope InviteSlot seed satisfying User.InsertValid's invite branch) and `seedBallot` (AdminSigning('ceb') + raw Ballot INSERT satisfying ProposedQuestion/ProposedOption BallotIdValid) — feeding wave-3 Plans 12.3-07 (Group E) and 12.3-08 (Group F).

## What Built

### `seedUserInvite(auth, newUser, overrides?)` — Layer-2.5 primitive

- Wraps the existing `IAuthorityEngine.createOfficerInvite` + `saveInviteWithSigning(_, 'rad', _)` chain to insert an `InviteSlot` row (Type='of') whose `(Cid, InviteSignature)` pair will satisfy `User.InsertValid`'s invite-bound branch when the downstream User row is inserted in Plan 12.3-07.
- Uses real engine methods only — no raw SQL fall-back was necessary because the engine already exposes the full officer-invite-save pipeline.
- Returns `{ inviteSlotCid, inviteSignature }`. The signature is taken from the freshly-generated `OfficerInviteShare` (engine-side `secp256k1.sign(...)` over the canonical officer-invite payload), then stored verbatim in the InviteSlot row by `saveInviteWithSigning`.
- Optional `overrides.officerInit` lets callers override `name` / `title` / `scopes` if a specific officer fixture shape is needed for a given test.

### `seedBallot(elec, ballotId?)` — Layer-3 helper

- Composes three SQL steps (no new engine surface — same pattern as `seedElectionSigning` + `addTestElection`):
  1. INSERT into `AdminSigning` with `Scope = 'ceb'` and `Digest(1, :id, :electionId, :authorityId, :description, :districts)` matching `Ballot.MutationValid`'s recompute formula exactly.
  2. `SigningEngine.sign(nonce, sig)` to auto-complete the OfficerSignature + AdminSignature (threshold=1 from the seeded admin policy).
  3. INSERT into `Ballot` with `with context SigningNonce = :nonce, Tid = 1, now = :now`.
- Default `ballotId = 'ballot-1'` matches the literal used by the two pending `elections.spec.ts` tests (`:441` addQuestion, `:469` addOption).
- Resolves `electionId` from the DB (`select Id from Election where AuthorityId = :authorityId limit 1`) since `electionEngine.election` is a private field on `ElectionEngine`.

## Decisions Made

- **`seedUserInvite` uses officer-scope (`'of'`) invites.** The schema's `InviteType` view is `(au|of|k|r)` — there is no `'u'` type. The User row is always created off the back of an officer/keyholder/registrant invite. Officer is the simplest of the three because `createOfficerInvite` and `saveInviteWithSigning(_, 'rad', _)` are already on the public `IAuthorityEngine` surface (used by `seedAuthorityInvite` for the parallel authority case).
- **Return shape `{ inviteSlotCid, inviteSignature }` instead of plan's `{ inviteSlotCid }` only** (Rule 2 — must_haves contract completion). `User.InsertValid` requires `context.InviteSlotCid is not null and context.InviteSignature is not null`; the caller would otherwise have no way to recover the InviteSignature value after the InviteSlot has been persisted (the engine never returns it). Plan's must_haves.truths explicitly say "seeds the User.InsertValid invite chain via real engine methods … mirroring seedAuthorityInvite" — handing back the inviteSignature is part of that mirror because the caller will bind it into the User INSERT context next.
- **`seedBallot` inserts a real `Ballot` row, not `ProposedBallot`.** The plan's must_haves say "seeds a Ballot row before addQuestion / addOption calls so ProposedQuestion.BallotIdValid and ProposedOption.BallotIdValid are satisfied." Both CHECK constraints (lines 714, 731, 781 of votetorrent.qsql) read `exists (select 1 from Ballot B where B.Id = new.BallotId)` — they reference the canonical `Ballot` table, not `ProposedBallot`. The schema comment on `ProposedQuestion.BallotId` (`-- references ProposedBallot.Id`) is misleading vs. the actual CHECK target.
- **`IElectionEngine.proposeBallot` is not sufficient.** It only inserts into `ProposedBallot`. No current engine method seeds the `Ballot` row (that insert lives downstream of an accepted proposal flow, which is not yet wired through Phase 12.x). The helper therefore composes the AdminSignature('ceb') + raw Ballot INSERT itself, mirroring `addTestElection`'s seedElectionSigning + raw ElectionRevision INSERT pattern.
- **`Tid = 1` matches `seedElectionSigning` / `respondToInvite` / `createAuthority` conventions** in this test-fixture layer. All Phase 12.2/12.3 helpers hard-code Tid=1; the AdminSignature Digest tuple uses the literal `1` rather than a bind variable so the formula is identical to what `Ballot.MutationValid` recomputes.

## Deviations from Plan

### Auto-added critical functionality

**1. [Rule 2 — Contract completion] Return `inviteSignature` alongside `inviteSlotCid` from `seedUserInvite`**

- **Found during:** Task 1 schema review (`User.InsertValid`).
- **Issue:** `User.InsertValid` requires both `context.InviteSlotCid` and `context.InviteSignature`. The plan's signature `seedUserInvite(...): Promise<{ inviteSlotCid: string }>` would force Plan 12.3-07 to either (a) re-query the InviteSlot row for its `InviteSignature` column, or (b) call `createOfficerInvite` itself just to read the signature — duplicating helper logic at every consumer.
- **Fix:** Return type expanded to `SeedUserInviteResult = { inviteSlotCid, inviteSignature }`. The `inviteSignature` value is the same hex string `createOfficerInvite` produced (passed verbatim into `saveInviteWithSigning`'s InviteSlot.InviteSignature column).
- **Files modified:** `packages/vote-engine/test/fixtures/test-context.ts` (same file the plan lists; no out-of-scope expansion).
- **Commit:** `b5c3053`.

### Other notes

- The plan mentioned an analogous `saveUserInviteWithSigning` engine pair as a possible alternative — none exists; `saveInviteWithSigning` already accepts `AuthorityInvite | OfficerInvite` and routes by `.type`. Using the officer branch is the canonical path. No engine work needed.
- Plan's `seedUserInvite(auth, newUser: User)` takes a `newUser` argument; this implementation accepts it (used only to default `officerInit.name = newUser.name`) and threads the rest through `overrides?.officerInit`. The unused-property warning is intentional — keeping the parameter in the signature for Plan 12.3-07 ergonomics (the caller wires up the newly-created user identity through the helper boundary).
