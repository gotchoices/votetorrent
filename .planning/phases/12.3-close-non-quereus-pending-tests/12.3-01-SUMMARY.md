# Phase 12.3 Plan 01: Align respondToInvite Digest with Authority.InsertValid Summary

**One-liner:** Replaced engine-side `JSON.stringify(invokes)` in `NetworkEngine.respondToInvite()` with a SQL-side `Digest(:tid, :authorityId, :name, :domainName, :imageRef)` call for authority invites, and rewired `createAuthority()` to reuse the reserved `InviteResult.InvokedId` as the new Authority.Id so `Authority.InsertValid`'s digest-match clause finally lines up.

## What Changed

### `respondToInvite()` — authority-invite branch

- For accepted authority invites (`invite.invite.type === 'au'` && `isAccepted`):
  - Generate `authorityId = crypto.randomUUID()` once at invite-response time.
  - Read `invokes.authority.{ name, domainName, imageRef }` from the typed payload.
  - INSERT into `InviteResult` with `Digest(:tid, :authorityId, :authorityName, :authorityDomainName, :authorityImageRef)` computed by the DB — no engine-side hashing.
  - Persist the generated id in `InviteResult.InvokedId`.
- For all other accepted invites (user / officer / keyholder / registrant) the legacy `JSON.stringify(invokes)` digest is retained — Group E (user invite chain) is the responsibility of Plan 12.3-07.
- For rejected invites (`!isAccepted`) the Digest column remains `null` per `InviteResult.DigestValid`.

### `createAuthority()` — reserved-id lookup

- When `options.inviteSlotCid` is provided, query `select InvokedId from InviteResult where SlotCid = :slotCid` and use the returned id as the new Authority.Id. This is required so the `Authority` insert's `(new.Id, new.Name, new.DomainName, new.ImageRef)` tuple reproduces the exact value `Digest()` was computed over inside `respondToInvite()`.
- When no `inviteSlotCid` is supplied (first-authority shoe-in path), behavior is unchanged — `crypto.randomUUID()` continues to be used.
