# Phase 12.3 Plan 09: Group H — Signing Equivalence Smoke Unskip Summary

Rewrites and unskips `signing.spec.ts:574` (REAL ENGINE equivalence smoke for the
`sign()` builder path) using two independent `startSigningSession` calls so the
`OfficerSignature (SigningNonce, UserId)` PK is not violated by a redundant
sign-on-same-nonce-and-user, while preserving the test's equivalence intent.

## What Changed

### `packages/vote-engine/test/signing.spec.ts` (lines ~574-660)

**Before:** Single test that called `startSigningSession` followed by an explicit
`engine.sign(nonce, sig)` on the same nonce + user. With threshold=1, the first
call already inserted the OfficerSignature row for `(nonce, user)`, so the
second `sign()` (or builder `commit()`) tripped the PK. The test was
`it.skip(...)` with a BLOCKED annotation.

**After:**
- Leg A — engine path: `engine.startSigningSession(authorityId1, ..., 'rad', sig1)`
  in `ctx1`. The internal `sign()` call for threshold=1 produces the
  OfficerSignature + AdminSignature rows. We read back `UserId / SignerKey /
  Signature` from `OfficerSignature where SigningNonce = :nonce1`, the
  `AdminSignature` row count for `nonce1`, and the `AdminSigning.Scope`.
- Leg B — builder path: `engine.buildStartSigningSession().fromPayload(...).commit()`
  in a SECOND fresh `ctx2`. This forwards to the same `engine.sign()` code path
  against a distinct `SigningNonce`. We read back the same observable fields
  for `nonce2`.
- Equivalence assertions:
  - `sessionA.thresholdReached === sessionB.thresholdReached === true`
  - Officer rows in each leg correctly attribute to that leg's user
    (`officerA.UserId === user1.id`, `officerB.UserId === user2.id`) with the
    correct `SignerKey` + `Signature`.
  - One `AdminSignature` row per nonce in each leg.
  - Both legs produce `AdminSigning.Scope === 'rad'`.
- Removed `it.skip(...)` and the BLOCKED annotation; replaced with a comment
  describing the structural PK reason for the two-session rewrite.

### Plan-wording vs. implementation

- The plan task text says "Leg B: Run the builder.fromPayload(...).commit()
  path, which will internally invoke sign() against the new nonce." Taken
  literally with `buildSign` (which calls `engine.sign(input.nonce, input.signature)`)
  on a nonce produced by a *separate* `startSigningSession` would re-introduce
  the PK collision (startSigningSession already auto-signed `nonce2 + user2` at
  threshold=1).
- The actually-equivalent path that satisfies "fresh nonce per leg + builder
  invokes sign() internally + no PK collision" is `buildStartSigningSession()
  .commit()` — the builder wrapper around the *session-start* API, which
  internally calls `engine.sign()` via `startSigningSession`. This matches the
  plan's verification line ("two `startSigningSession` calls in the rewritten
  test") and CONTEXT.md option (a)'s explicit description ("fresh nonce +
  signing session for each leg... comparing observable Officer/Admin signature
  state rather than re-using one session").
- Implementation choice noted in code comment so the future reader sees why we
  did NOT additionally call `eng.buildSign().commit()` (which would re-trigger
  the PK).
