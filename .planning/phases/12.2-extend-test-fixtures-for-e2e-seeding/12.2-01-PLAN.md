**Part A: Split-batch fix for NetworksEngine.create()** (lines 99-194)

Split the single-batch `db.exec()` call in `NetworksEngine.create()` into sequential `exec()` calls so that the `Admin` INSERT commits before the `Officer` INSERT runs. Quereus 3.2.1 evaluates `Officer.AdminValid` CHECK eagerly during each INSERT, not at batch end.

Split into three sequential `exec()` calls with the same parameter object:

1. First exec: User + UserKey + Authority + Admin (4 INSERTs) -- all have no cross-table forward dependency within this group
2. Second exec: Officer (1 INSERT) -- depends on Admin existing, so must run after first exec
3. Third exec: Network (1 INSERT) -- depends on Authority existing, already committed in first exec

Keep every context binding, parameter key, and interpolated `${tid}` value unchanged. Wrap each `exec()` call in the existing `try/catch` error handler block (same QuereusError/MisuseError rethrow pattern). The `catch` block at lines 195-203 becomes the outer try/catch wrapping all three sequential calls.

**Part B: Split-batch fix AND invite context params for NetworkEngine.createAuthority()** (lines 54-119 in network-engine.ts)

Apply the split-batch fix: split into sequential exec() calls:
1. First exec: Authority + Admin (2 INSERTs)
2. Second exec: Officer (1 INSERT)

Additionally, extend the `createAuthority()` method signature to accept an optional third parameter for invite context:
`async createAuthority(authority: AuthorityInit, admin: AdminInit, options?: { inviteSlotCid?: string; inviteSignature?: string }): Promise<void>`

Change the hardcoded context bindings from:
`with context SigningNonce = null, InviteSlotCid = null, InviteSignature = null, Tid = :tid`
to use the optional params:
`with context SigningNonce = null, InviteSlotCid = :inviteSlotCid, InviteSignature = :inviteSignature, Tid = :tid`

And add to the parameter object:
`inviteSlotCid: options?.inviteSlotCid ?? null`
`inviteSignature: options?.inviteSignature ?? null`

This is required because `Authority.InsertValid` (votetorrent.qsql line 66-78) has two paths: (a) first authority (count=1, no invite needed) or (b) second+ authority (requires `InviteSlotCid is not null AND InviteSignature is not null` with a matching InviteResult row). Without passing invite context, `seedAuthorityInvite()` in Plan 02 cannot enable the 4 createAuthority tests in Plan 03 even after seeding InviteSlot/InviteResult rows.

The `INetworkEngine` interface in vote-core declares `createAuthority(authority: AuthorityInit, admin: AdminInit): Promise<void>`. The optional third parameter is backward-compatible -- callers without it still compile. No interface change needed.

Keep the same tid binding (currently hardcoded as `tid: 1`), same catch block shape.
